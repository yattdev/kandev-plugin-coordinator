# Vendor provenance — Coordinator policy contract

This records exactly what is vendored under `docs/contracts/upstream/`, from
where, and how to refresh it. It exists so a reviewer (or CI) can answer
"is this vendored tree exactly what it claims to be?" without trusting a
free-text commit message.

## Immutable source (current pin)

| Field | Value |
| --- | --- |
| Source repository | `yattdev/tasks-coordinator` |
| Source branch | `feature/codify-coordinator-p-8eu` |
| Source commit (exact SHA) | `2ca27d00477dc298fc91187274968f1fc3970fef` |
| Contract | `docs/contracts/coordinator-policy-contract.json` |
| Contract version | `1.1.0` |
| Contract digest (`sha256`) | `00bc80871b666c17abacb96382f3e01291421cc8fe4b726f539fc613cdfb84a4` |
| Validator | `docs/contracts/validate_contract.py` |
| Validator schema | `1.1.1` |

These same six values are cross-checked, hermetically (no network), by
`scripts/verify_contract_provenance.py` against `docs/contracts/upstream-manifest.json`
and against the vendored files' own content (`contract_version`, `digest`,
`VALIDATOR_SCHEMA_VERSION`). The `source_repository`/`source_branch`/
`source_commit` above are additionally, independently pinned as hardcoded
constants in `scripts/contract_pins.py` — `verify_contract_provenance.py`
checks the manifest's provenance block against those constants (not merely
against itself), and `scripts/generate_contract_manifest.py` refuses to
write a manifest whose `--source-repository`/`--source-branch`/
`--source-commit` disagree with them, so an arbitrary fork, a different
branch, or a mutable ref (a branch name, tag, or short SHA) in place of the
pinned full commit SHA can never be vendored or silently accepted as
provenance. `make verify-contract` runs that check plus the full vendored
validator/test/adversarial-sweep suite and the isolated regression tests in
`scripts/test_verify_contract_provenance.py` (see [`README.md`](README.md)).

Per the source repository's own vendoring rule (`CONTRACT_MAPPING.md` §4.3):
updating the contract (upstream) and updating this plugin's vendored copy are
**separate reviewed changes**. This vendoring change never edits the source
repository, and this repository never bumps `contract_version` on its own
initiative — it only re-vendors what a fresh, already-approved source SHA
declares.

## What is vendored, byte-for-byte

`docs/contracts/upstream/` is an **exact, unmodified copy** of the source
repository's `docs/contracts/` directory at the pinned SHA above — every
file's sha256 is recorded in `docs/contracts/upstream-manifest.json`:

- `coordinator-policy-contract.json` — the contract itself.
- `validate_contract.py` — the standalone validator (stdlib-only, no
  third-party dependencies).
- `adversarial_sweep.py` — the reproducible 78-mutation adversarial sweep.
- `test_validate_contract.py` — the upstream unit test suite (fixtures +
  canonical contract + snapshot/overlay checks).
- `CONTRACT_MAPPING.md` — the field-by-field provenance/evolution-rules
  reference (authoritative interpretation of the contract, not reinterpreted
  here).
- `fixtures/*.json` — every positive/negative fixture the upstream test
  suite and adversarial sweep exercise.

Nothing in `docs/contracts/upstream/` is hand-edited. A change to any file in
that directory that is not a full re-vendor (see below) is a vendoring bug.

## What is this plugin's own (not vendored)

- `docs/contracts/plugin-snapshot.json` — this plugin's machine-readable
  `defaults` dump, validated against the vendored contract by
  `validate_contract.py plugin-snapshot`. Currently identical in content to
  the upstream `fixtures/valid_plugin_snapshot.json` positive control: this
  plugin declares exactly the floor the contract requires and narrows
  nothing further today. If the plugin later needs additional
  workspace-specific defaults, extend `defaults` here — never weaken the
  four mandatory keys.
- `docs/contracts/upstream-manifest.json` — generated by
  `scripts/generate_contract_manifest.py`; records the sha256 of every
  vendored file plus the provenance table above, in machine-readable form.
- `scripts/contract_pins.py` — the independently pinned
  `source_repository`/`source_branch`/`source_commit` constants; the only
  place those three values may be changed, and the only source of truth
  `verify_contract_provenance.py` and `generate_contract_manifest.py` trust
  for them.
- `scripts/verify_contract_provenance.py` — hermetic (no network) proof that
  the files on disk still match the manifest, and that the manifest's
  provenance still matches `scripts/contract_pins.py`.
- `scripts/generate_contract_manifest.py` — regenerates the manifest; run
  only as the last step of a deliberate refresh (below). Refuses to run
  against a `--source-repository`/`--source-branch`/`--source-commit` that
  disagrees with `scripts/contract_pins.py`.
- `scripts/test_verify_contract_provenance.py` — isolated regression tests
  for the two scripts above (missing/attacker/mutable/substituted
  provenance, symlinked vendored files, path traversal, malicious generator
  input).

## Deterministic refresh procedure

Run this only when the source repository has produced a **new, already
Review- and QA-passed** immutable SHA whose `docs/contracts/` you intend to
adopt. Never edit vendored files by hand; always replace the whole tree.

1. Identify the new source SHA (must itself have passed independent Review
   and QA against that exact SHA — this repository does not re-derive that
   approval).
2. Update `scripts/contract_pins.py`'s `EXPECTED_SOURCE_REPOSITORY` /
   `EXPECTED_SOURCE_BRANCH` / `EXPECTED_SOURCE_COMMIT` to the new
   repository/branch/exact-SHA **first**. Every later step in this
   procedure (the manifest generator, the hermetic provenance check, and
   CI's `contract-vendor-provenance` job) validates against these three
   constants, so a refresh cannot proceed against a stale or mismatched
   pin.
3. From a checkout of `yattdev/tasks-coordinator` at that exact SHA, replace
   `docs/contracts/upstream/` in this repository wholesale:
   ```sh
   rm -rf docs/contracts/upstream
   mkdir -p docs/contracts/upstream
   cp <source-checkout>/docs/contracts/coordinator-policy-contract.json docs/contracts/upstream/
   cp <source-checkout>/docs/contracts/validate_contract.py docs/contracts/upstream/
   cp <source-checkout>/docs/contracts/adversarial_sweep.py docs/contracts/upstream/
   cp <source-checkout>/docs/contracts/test_validate_contract.py docs/contracts/upstream/
   cp <source-checkout>/docs/contracts/CONTRACT_MAPPING.md docs/contracts/upstream/
   mkdir -p docs/contracts/upstream/fixtures
   cp <source-checkout>/docs/contracts/fixtures/*.json docs/contracts/upstream/fixtures/
   ```
3. Regenerate the manifest (records the new sha256 set plus the new
   contract_version/digest/validator schema read back from the files just
   copied). The flags below are a fail-closed confirmation, not free-form
   input: the script refuses to run if any of them disagree with the
   `scripts/contract_pins.py` values updated in step 2.
   ```sh
   python3 scripts/generate_contract_manifest.py \
     --source-repository yattdev/tasks-coordinator \
     --source-branch <new-source-branch> \
     --source-commit <new-exact-sha>
   ```
4. Update the provenance table at the top of this file to match.
5. Review `docs/contracts/plugin-snapshot.json` against the (possibly
   changed) mandatory `defaults` keys; update it if the new contract version
   adds a mandatory key this plugin does not yet declare.
6. Update the pinned SHA in `.github/workflows/ci.yml`'s
   `contract-vendor-provenance` job: both the `ref:` under "Check out pinned
   immutable contract source" and the `expected_ref` asserted in its
   "Cross-check pinned ref against scripts/contract_pins.py" step, to the
   same new exact SHA already set in `scripts/contract_pins.py` (step 2).
7. Run `make verify-contract` locally and confirm it passes end to end
   (contract, plugin-snapshot, overlay fixtures, full vendored test suite,
   78/78 adversarial sweep, the hermetic provenance check including the
   independent pin re-check, and the isolated provenance regression tests).
8. Commit the whole refresh as one coherent change; do not mix it with an
   unrelated code change. Per upstream's rule, this refresh is reviewed on
   its own.

If the plugin's `plugin_contract_version` / `vendored_digest` is left
pointing at an older pin while `contract_version` in the freshly vendored
contract has moved on, `validate_contract.py plugin-snapshot` fails closed
(`stale_version` / `stale_digest`) rather than silently treating the old
snapshot as still valid — this is intentional (see
`docs/contracts/upstream/CONTRACT_MAPPING.md` §4 point 3).
